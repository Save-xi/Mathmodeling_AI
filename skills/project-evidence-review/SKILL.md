# 项目证据二审

把用户或另一任务给出的完成声明当作待核验输入。交付的核心是“声明—实际实现—运行证据—剩余缺口”，默认用中文。

## 确定本次审查对象

- 从最新用户要求确定目录、分支、目标和交付范围。先读当前 README 与适用的 AGENTS.md；记忆和旧报告只用于找线索。
- 复核另一个 Codex 任务时，先用当前可用的任务工具读取其最近完成回合。`notLoaded`、归档和中断不等于工作失败；概述中的完成声明也不等于已验证。
- 用户要求等待上游完工时，先做独立资料准备，用可用的状态等待工具等待真实完成后再审正式产物；不要另开用户任务或擅自给它发送指令。
- 对 Git 项目记录实际 checkout、HEAD 和用户已有改动；可以为读取文件和执行检查设置正确的命令工作目录。审查本身不授权切换用户当前分支、重置或替换工作树；比较历史版本优先用只读 Git 命令。日期和提交号只是本次记录，不为项目新增哈希、收据或冻结门槛。

## 沿实际执行链核查

1. 读原始项目书/题面、当前源码入口、配置和报告。先确定实现实际接收什么、输出什么，再比较拟用算法；类名、依赖列表和路线图不证明模型已接入运行。
2. 先用 `rg` 定位源码。查结果时单独检查已知 `outputs/`、`reports/`、`data/` 等路径；必要时在这些明确目录内用 `rg --files --hidden --no-ignore`。普通搜索零命中不足以证明被 gitignore 排除的结果不存在。不要扫描权重/视频全文。
3. 对关键声明标注：已实现且有本次验证、已实现但仅有历史运行证据、接口/占位、计划、未找到/材料不足。区分未找到证据与已证明不存在。
4. 只复跑能改变审查结论的最小关键检查：检查命令、解释器、输入、退出码、数值和产物是否对应。已有检查通过后，除非代码变化或新疑点出现，不重复整个测试菜单。
5. 将环境/权限错误与算法失败分开；必要时使用 `$codex-task-recovery`，或直接按同等步骤确认目录、解释器、临时文件和工具错误。
6. 图表、PDF、演示和交互性声明需要真实视觉/交互证据；结构验证或编译只支持对应层级的结论。涉及离线代理目标、仿真、硬件或因果主张时，按实际测量边界表述。

## 给出可执行结论

用一张紧凑表格承载真正影响决策的条目：

| 声明/目标 | 当前实现位置 | 本次检查或历史证据 | 判定与缺口 |
|---|---|---|---|

优先说明阻断目标的错误，其次是需要补测的主张。每个修复建议给出具体文件/入口、原因和能关闭问题的检查；不把已经撤销的范围重新包装成待办。

下一步围绕最重要的一个证据缺口，说明投入理由、可比较基线和继续/停止条件。用户仅要求审查时保留代码；用户已要求修补时继续完成范围内的修补及验证。

数模建模/论文终审由现有 `$mathmodeling` 承接，国赛语言工作由 `$guosai-paper` 承接。不要复制它们的整套规则，或把本技能当成科研正确性认证。
